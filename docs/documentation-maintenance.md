# 文档维护约定

更新日期：2026-11-12。

## 主动记录的时机

用户已授权 Agent 在协作过程中自动发现并沉淀有复用价值的信息，无需逐次询问是否记录。以下情况应检查是否需要更新相关文档：

- 用户明确确认或修正了长期协作偏好、执行规则、系统边界。
- 通过代码或配置核实了重要行为、依赖、接口契约或版本限制。
- 完成排障并确认了原因、处理办法及适用条件。
- 任务留下后续 Agent 必须知道的阻碍、未完成工作或验证步骤。
- 本次工作发现已有说明过期或与用户最新要求冲突。

每个经手 issue 都需要持续沉淀；只维护本次涉及的资料，不为每条消息或命令输出单独建文档。用户明确要求 `push` 时直接执行，不在该流程中插入文档整理。不得记录密钥、口令或其他秘密。

## 按 issue 沉淀

用户于 2026-11-12 明确确认：一个 issue 对应一条业务分支和一个 PR 的开发模式；每个经手 issue 都要沉淀，覆盖实际做过的工作、问题、处理办法、结果、重要判断和未解决项，不仅记录已泛化的经验。开发分支到 release 交付分支的重建属于同一 issue 的交付阶段，不另开一份 issue 记忆或另一条 PR 交付线。

“经手”的范围按[issue 入口](issues/README.md)判断；仅扫描列表不逐条建档，实质参与或重要发现才按 issue 记录。没有改代码、没有踩坑、只做调研/review/依赖核验，也要留下实际活动与结论；对他人 issue 调研获得的重要接口、依赖、风险、实现位置或验证信息，同样按对应编号记录，并注明自己是调研者而非实现负责人。未验证的判断明确标注；不能据他人状态或自己的调研宣称完成实现。

本地 Git 任务记录只保存工作现场，不能作为唯一长期落点。固定入口为 `docs/issues/ISSUE-ID.md`，具体读写与回流见[Issue 知识入口](issues/README.md)；附 issue/PR/commit、核验时间和依据，已有验收或调研文档链接复用，避免复制。没有新发现也如实记录做了什么、确认到什么范围。跨 issue 可复用的规律另更新对应主题/skill，并从 issue 记录链接过去；AGENTS 仍只保留稳定规则和入口。

开始/恢复 issue 先检索编号及关联 issue 的既有记录，再按需实时核验；按[issue 入口](issues/README.md#工作过程中持续更新)在自然节点合并更新，重要阻碍与决策及时保存，交付/暂停/结束前检查遗漏并回流个人基础。只读调研允许沉淀本地知识，不因此认领他人任务、创建业务分支/PR 或修改 Linear。旧记录只按已有可核验材料补齐，不伪造历史经历或验证结果。无 issue 的工作也按已有主题或本地 task 保存相关经验，不编造编号。

## 经验的依据、有效性与修剪

| 信息类型 | 保存与使用方式 |
| --- | --- |
| 用户明确确认的长期偏好/边界 | 更新已有稳定规则，标清适用范围；新的明确指令替代旧规则。一次例外授权不扩大为长期权限。 |
| 已验证的项目事实/排障经验 | 在原主题写触发条件、依据与核验日期、适用版本/环境、最小处理和失效条件；推测标为待验证，不直接进入通用前置。 |
| 当前任务状态 | 共享 Git 任务记录只保存继续执行所需的目标、阻碍、下一步及知识链接；长期 issue 记录保留实际经历、结果与决策依据，不复制执行状态全文。 |
| Agent 对习惯或原因的推测 | 只作为当前假设；不能仅凭一次行为写成用户偏好。影响范围/授权时仍以明确指令为准。 |

读取经验时检查失效条件：相关上游规则、SDK/Node/生成器、接口契约、目标部署或任务范围变化后，只重验受影响的结论。稳定偏好不因时间经过而反复询问；实时状态不能仅因文档有日期而当作当前事实。新证据推翻旧结论时修改原入口，删除失效的执行要求，必要历史保留日期与链接。

经验被代码修复或上游吸收后，撤掉已无作用的人工前置。用户再次纠正相同偏好、重复踩已知坑、反复调研相同材料、重写已有工具或恢复时找不到现场，都是检查沉淀是否有效的触发点：查入口是否可发现、条件是否准确、是否只留在旧分支，并修正原有落点。每个 issue 必须有可检索的工作与经验记录；简单成功任务也记录做了什么、确认了什么以及经验落点，不强制长篇复盘，不新增评分或命令流水账。

版本化文档提供可检索记忆，不等于模型持续训练。判断效果看能否减少重复提问、重复调查和重复踩坑；同一问题再次发生时先修正原入口、条件或失效说明，不另写重复复盘，也不新增评分门禁。

一次故障先记 issue/专题；只有确认会重复影响多个任务、尚未被代码自动解决时，才升级为公共执行前置。用户明确的稳定偏好可直接更新规则；一次例外或环境成功不能自动推广。根 AGENTS 保留关键判断与索引、控制在 150 行以内，详细步骤留在专题，不以填满额度为目标。

## 旧开发分支使用新经验

个人基础上的知识回流不会自动更新旧开发分支。恢复任务时通过最新版工具的 status 查看个人基础位置和自任务基线以来的知识路径变化，只读取当前任务相关的文档/skill；AGENTS 与文档里的稳定个人约定可从基础 worktree 查阅，业务语义、分支特定规则和固定依赖仍核对目标 checkout。临时未提交的基础规则须先核实，不当作已经发布的稳定经验。

不要为读取新规则整支合并个人基础。从基础目录调用支持目标参数的最新工具；检查其运行时与目标兼容性，不假定工具能处理任意旧版本。确需工具补丁进入需求分支时才选择性转移；任务结束按原流程回流。启动入口见[任务上下文与恢复](linear-development-workflow.md#任务上下文与恢复)。

## 功能分支知识回流

Agent 已获常规开发中的选择性回流授权。确认可复用的知识/工具与业务分开提交，在开发切片收尾、跨会话交接或 PR 整理前，按[双路径流程](linear-development-workflow.md#开发与主动沉淀)主动回流个人基础；不等用户提醒，不整支合并。回流完成记录目标提交，未完成说明具体现场和原因。PR 阶段优先直接在个人基础记录经验，避免随后重写业务历史。

单一事实只维护一个当前入口；skill 描述触发时机和操作决策，docs 放细节，本文件与 AGENTS 不重复列所有工具。规则变更同时修正现有引用，历史记录保留原观察日期。无需为每次提交新增文档、索引项或记录机器日志。共享记录只保留继续工作必需的结论；个人绝对路径、原始报告和临时任务状态留在 Git 共享目录或忽略目录。

## 内容放在哪里

- 根目录 `AGENTS.md`：简短、稳定、需要 Agent 执行的规则，以及关键文档入口。
- `docs/` 主题文档：背景、设计理由、数据流、证据、操作方法、限制和排障经验。
- 阶段性交接内容：优先放在对应主题中；确有必要才单独建文档，并标明日期、完成情况和下一步。
- `docs/README.md`：维护主题入口和适用场景，避免把详细正文复制到索引。

文档正文使用中文，表达简明、准确，便于人类和后续 Agent 阅读；文件名保持稳定并能表达主题。代码示例及其中的注释使用英文；命令、路径、配置键、专有名称及需保真的原始引用保留原文。Git commit 信息、PR 标题、正文及审查评论使用英文。先搜索已有文档，优先原地更新。与上游已有资料重复的内容以链接和必要的项目差异说明为主。

## 面向接手 Agent 的写法

让未参与原会话的 Agent 能独立理解并开展工作：

1. 开头说明主题、适用范围和结论；涉及易变状态时标明核验日期。
2. 给出相关仓库、文件、分支、配置项和可复核的证据链接。命令应注明工作目录，并说明是否会修改状态。
3. 区分用户确认的要求、代码验证的事实、尚未接受的提案和待验证事项；不能把建议写成已完成实现。
4. 涉及阶段状态时写清完成了什么、如何验证、尚未验证什么，以及下一步的具体入口；不保留冗长会话过程。
5. 区分本地机器配置与仓库可共享配置，不能假定后续 Agent 的环境相同。

## 把环境经验提升为执行前置

用户确认的目标是：经验能影响下一次任务的执行顺序，而不只是事后留下记录。确认环境问题的原因和处理办法后，应在当前任务内完成以下沉淀：

1. 在已有主题文档记录触发条件、错误特征、已确认原因、最小处理步骤、验证结果、适用环境及日期；尚未证实的原因明确标为待验证。
2. 将可复用的预防或诊断步骤提升到通用执行入口。详细步骤更新对应专题；只有必要的预防条件才补[执行前索引](coding-and-self-review.md#执行前的环境检查与顺序)，故障特征补[诊断入口](agent-failure-diagnosis.md)。写清“何时先做什么、成功后再做什么、仍失败如何处理”，不能只要求下次阅读历史验收报告。
3. 区分已通过代码修复而自动生效的经验、需要执行前准备的条件，以及仅在出现特定错误时使用的诊断步骤，避免给所有任务增加无关检查。根 `AGENTS.md` 只保留稳定规则和必要入口，索引同步注明适用场景。
4. 通用入口链接主题证据，不复制完整日志或维护两套操作细节。涉及可重复且规则明确的操作时，按[自动化工具沉淀约定](automation-tools.md)判断是否值得固化为工具，并验证实际效果。

经验沉淀不扩大操作授权，不改变直接 `push` 流程；不得把一次成功写成无条件适用的结论，也不得让环境诊断静默掩盖真实代码错误。后续发现条件变化或步骤失效时，同步修正通用入口和主题说明。

## 更新与核验

用户最新明确要求优先于旧文档。发现冲突时，更新相关正文和入口，避免留下两套相反规则；存在未明确的行为或契约时，向用户澄清后再记录为结论。

仅记录已完成的核验，不因编辑文字就声称事实已重新验证。更新后检查相对链接、文件路径及规则一致性，并在任务结果中简短说明沉淀位置。纯文档变更不需要运行 UI 测试或构建。


## 本地链接与锚点检查

修改本文档体系后，从基础设施 checkout 根目录运行 `yarn agent:docs-check --file docs/PATH.md`，可重复传入 `--file` 精确选择本次相关 Markdown（最多 50 个），无需为每轮任务重写临时链接检查脚本。路径相对基础设施仓库根目录，不依赖终端当前目录；不会自动扫描、修改文件或调用 Git。

```sh
yarn agent:docs-check --file docs/agent-task-start.md --file docs/solana-agent-friendliness-roadmap.md
```

纯文档更新只运行上述链接检查及差异审查；修改检查器本身才按影响运行 `yarn test:agent-docs-check` 或统一工具回归。

实现：[agent-docs-check.mjs](../scripts/agent-docs-check.mjs)。仅使用 Node 内置模块，离线读取指定文件及本地 Markdown 锚点目标；单份 Markdown 最大 2 MiB。支持行内显式链接及图片 `](PATH)`、尖括号包裹的路径、百分号编码、同页片段、仓库内相对文件/目录与 ATX（`#` 至 `######`）标题；中文、行内代码/星号强调的标题文本及重复标题后缀纳入锚点计算。目录只检查存在，非 Markdown 文件不验证行号或片段语义。

fenced 代码块和匹配的单行反引号代码跨度不作为链接检查；外部 http/https、mailto、app/plugin 及协议相对 URL 仅计数跳过，不访问网络。引用式链接/定义、HTML 链接、含 title 或嵌套括号的行内链接、缩进链接、跨行代码跨度/链接、本地查询参数及非 Markdown 片段不在支持范围；可识别的不支持语法明确报告，不静默改写或猜测。Setext、HTML/entity 或代码跨度外含下划线的标题的目标页锚点拒绝验证；本工具不是完整 Markdown 渲染器，复杂结构需人工或相应渲染器核对，passed 仅表示本次所选文件中支持语法的本地链接检查通过。

绝对源路径、越出仓库的目标、最终符号链接及经祖先链接解析到仓库外的路径明确拒绝；不读取任意外部目录。只对锚点目标读取 Markdown，普通文件目标只检查存在/类型，不执行内容。输入摘要记录实际读取的 Markdown；它不是持续监控或原子快照，不证明文档内容真实、命令可执行、环境就绪或线上 URL 可达，也不自动检查未选文件中的入链。

stdout 的 JSON 包含 scope、status、selected、本地链接检查数、外链跳过数、Markdown 输入摘要与 diagnostics（file/line/code）。计数是实际处理的链接，不是完整覆盖证明；某行失败后该行剩余链接不继续解析，其他行/文件继续。退出 0 表示所选检查通过，1 表示文档/路径/语法诊断，2 表示参数错误；错误详情查看 JSON，不能只搜索日志里的 passed。需要保存证据时重定向到本次忽略目录，不提交机器报告。此入口不运行 `git diff --check`，差异/命令归属/历史搬移完整性仍按任务单独核对。
