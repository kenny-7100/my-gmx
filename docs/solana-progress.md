# Solana 迁移实际进度评估

本流程于 2026-10-24 经用户确认，入口为 [gmx-solana-progress](../.agents/skills/gmx-solana-progress/SKILL.md)。目标是评估实际完成的迁移工作量，结合实时 Linear 与多个仓库的真实代码提供两个进度口径，并输出可直接使用的中英文简述。

## 两个口径与完成标准

| 口径 | 分母 | 含义 |
| --- | --- | --- |
| 现有需求范围进度 | 本轮 Linear 中全部有效迁移需求归并、去重后的工作量 | 已列出的迁移工作实际完成多少 |
| 完整迁移进度 | 按已确认完整迁移标准所需的全部工作量，包括未建单的必需缺口 | 距完整完成迁移还有多远 |

两者均为工作量估计，不按 Done 条数计算，不等同于上线就绪度或工期预测。现有需求范围不以 FESOL 团队总数为分母：排除旧 `GMTrade` 维护需求，按实际范围纳入其他团队的迁移需求；项目与标签冲突按[查询规则](linear-requirements.md)处理。取消项不增加剩余工作，重复项归并；被新方案替代的旧代码，只计当前目标仍可复用的成果，不把历史投入当作完成量。

完整迁移的基准：在现有 GMX 架构和统一数据流下承接已约定的 Solana 产品能力，旧前端退出不再影响这些能力，并消除对旧后端的长期依赖。每轮依据用户确认、最新需求和架构决策形成带版本/日期的完成标准，不从旧前端功能清单自动推导必须迁移的全部功能。

按标准检查产品功能、数据与计算、钱包和交易、历史、必要的安全与错误恢复、状态隔离、EVM 兼容、部署监控及人工验收。Crypto-only 首发与完整迁移分开：TradFi 等已确认后续范围属于完整迁移时纳入；尚未确认的范围列为待确认项，不自作主张加入确定分母。只有影响口径且无法从现有证据确定的问题，才简短向用户澄清。

## 取证步骤与覆盖

### Linear

- 按 [gmx-linear-requirements](../.agents/skills/gmx-linear-requirements/SKILL.md) 同步全量并读取正文和状态。核对范围、验收条件、层级、拆分、取消、重复及旧方案；不能仅统计标题或状态。
- 沿迁移需求、项目及相关链接查询其他团队的 API、SDK、设计、协议和基础设施需求。工具仅覆盖 FESOL 时，使用可用的只读 Linear API/连接器补充；无法访问则明确覆盖缺口，不能宣称读完所有相关团队。
- 对影响范围、完成判断、验收结论或关键阻塞的条目实时补读评论和双向关系；不必重复抓取与结论无关的所有附件，但未读取的设计/附件影响验收时须保留缺口。

### GitHub、多个分支及本地代码

先按[参考仓库说明](solana-reference-repositories.md)建立本轮相关仓库清单。主前端、gmx-api 及实际涉及的 SDK、协议、架构和索引项目按需纳入；旧前端和旧后端用于行为对照，不能计作目标架构已完成。

1. 在线分页枚举相关仓库的分支、开放 PR 和相关已关闭/已合并 PR；记录仓库、remote、目标分支和分页覆盖。不能只搜索带 `solana` 的分支名或只看开放 PR。结合需求编号、旧编号、父子任务、正文链接、提交信息和改动路径识别关联工作。
2. 对识别出的所有相关分支/PR 核对 head SHA、base、实际代码和差异。多个 head 相同或共享实现可复用读取结果；无关分支记录排除依据，不逐行审查无关代码。相关分支未挂 PR 也要纳入，只有分支名、无法读代码的不能算已验证。
3. 在线确认上游目标分支的最新 SHA。主前端交付基线为 `release`；其他仓库按真实发布流程核实，不能一律假定也叫 `release`。本地 remote-tracking refs 不代表在线最新；优先用 GitHub CLI/API 读指定提交的文件和比较结果，不自动 fetch/pull 或改动分支。
4. 查看相关调用路径、共享状态入口、契约、未解决审查意见及最新 head 的 CI/自测证据，检查回退、后续修改和重复实现。需要判断具体正确性时按[编码与自审规范](coding-and-self-review.md)读取适用的 gmx-prompts 细则；评估不是全仓库完整代码审计。
5. 只读检查本地工作区与相关本地分支，区分未提交、未推送、开放 PR、上游合并与部署状态。只有在目标架构可复用且有代码依据时，未交付实现才可计入开发成果；不把它表述为已经上线。
6. 按工作包核对 API 实际是样例还是真实链上数据、SDK/IDL/协议部署版本、必要配置和部署/人工验收记录。源码、CI 通过或 merged 均不能单独证明端到端能力可用；无权限查部署时明确未知，不发送交易或自行部署。

完整相关分支列表可能随查询变化，记录开始/结束时间。明确已访问和未访问的仓库、分支、PR、需求及部署边界；权限、分页或网络失败不能静默变成“没有相关工作”。

## 工作包、权重与完成量

建立互不重叠的工作包，而非给每条 issue 一票。可按网络与运行隔离、钱包资产、市场数据/API、共享交易状态、计算、下单和执行追踪、持仓管理、历史、Pools 及其他已确认产品能力组织；这只是归类示例，不是预设范围或固定权重。

每个工作包至少记录：

| 字段 | 内容 |
| --- | --- |
| 范围与归属 | 稳定工作包 ID、验收结果、对应需求、属于哪个分母，排除/归并原因 |
| 工作量 | 相对权重及依据：实现复杂度、改动面、跨仓库整合、验证和剩余交付工作；已有可靠 estimate 可参考但需校验一致性 |
| 实际成果 | 已完成的可复用子范围、代码/PR/提交链接，相关 base/head SHA |
| 交付与验收 | 未提交/未推送/PR 待合并/上游已合并/部署及真实验收证据分别记录 |
| 剩余与不确定性 | 尚缺实现、集成、审查修复、资源或验收；完成比例的低值/中心/高值及理由 |

父任务只作聚合，子项计量后不再重复计父任务；原需求与拆分切片按验收范围划分。多个分支的同一实现只计一次；互斥方案不能相加。即使 Done，存在实质缺口也按当前证据评估；即使 Todo，已有目标架构可复用代码也可计入有证据的完成量。

采用相对工作量单位，说明权重依据，不用行数、提交数、issue 数或消耗时间直接代替工作量。不预设“代码完成 70%、合并 90%”等状态系数。按已完成与剩余的具体子工作估算，包括必要的集成、修复和验收；最终交付/验收未完成时不能标 100%。明确展示重要的已开发未交付能力，避免工作量百分比掩盖上线阻碍。

两个口径使用同一工作包的相同权重和完成估计。令 `w_i` 为相对工作量、`c_i` 为实际完成比例，则各口径进度为 `sum(w_i * c_i) / sum(w_i)`。先确定范围和有依据的权重，再计算，不为得到期望数字倒推权重。若权重本身不确定，对合理的权重方案和完成低/高值做敏感性检查，报告估计区间；该区间不是统计置信区间。

一般取整数约数，证据粗糙时按 5 个百分点取整，不给小数制造精确感。置信度按覆盖完整性、契约确定性、代码/验收证据和权重敏感性给高/中/低及原因，两个口径可不同。影响总量的未知范围较大或关键仓库无法核实时，暂停数字结论，提供已确认事实和缺口；不将未知当零或已完成。

## 未建单缺口与范围变动

完整迁移口径主动检查需求覆盖缺口，尤其是仍依赖拟废弃服务、未覆盖的错误恢复、数据/计算契约和集成验收。每项缺口必须链接已确认完成标准与具体代码/契约证据，说明已有需求或 PR 是否覆盖。

已确认必需且未覆盖的工作加入完整迁移分母；纯设想和未确认产品范围单列情景，不自动建单。为两个分母使用共同的覆盖映射：超出已确认完整迁移标准的 Linear 范围应显式说明，而不是悄悄删掉或强行假定第二个进度必然更低。

## 本地记录与历史比较

默认保存到被 Git 忽略的 `.local/solana-progress/<UTC timestamp>/`，每轮保存 `assessment.md`（结论、范围与方法）和 `evidence.json`（仓库/分支/PR SHA、需求映射、工作包权重与完成区间、缺口及来源链接）。两者都不含凭据。复用 Linear 快照路径，不复制一套同步器；本轮纯手工结构化记录即可，不为未验证的 API 格式预建采集脚本。

保存完并验证计算、去重和覆盖后，才更新 `.local/solana-progress/latest.json` 指向该轮目录。失败或关键取证未完成时，可保留标明不完整的记录，但不得更新最新指针或覆盖历史。部分信息受限仍能形成有依据的完整评估时，应注明限制和置信度；不能省略未知项来制造完整性。

对照上一轮，分别解释实际推进、分母增减（新增/取消/确认缺口）以及证据/估算修正。必要时在相同范围和权重下再比较一次，避免把分母变化当作退步；首次评估没有历史基线，不编造趋势。

## 面向用户的输出

默认用中文解释并提供下表；数字只有实际评估后填写，模板变量不是预估结果。

| 进度口径 | 约数 | 估计区间 | 置信度 |
| --- | --- | --- | --- |
| 现有有效 Linear 迁移需求工作量 | 待核验 | 待核验 | 待核验 |
| 已确认完整迁移标准所需工作量 | 待核验 | 待核验 | 待核验 |

注明两个分母的范围及主要排除项。各用一个简短段落提供中文现状和英文现状，事实、数字、范围和确定性保持一致：说明完成到哪里、主要剩余工作、当前瓶颈，以及必要的已开发未交付区别。不要将旧项目成果当作新架构已完成，不输出未经证实的上线承诺。

随后只列关键证据、主要缺口及与上一轮的变化，链接详细本地记录；注明北京时间核验时间和覆盖边界。百分比不是发布日期，未解决的关键上线阻碍应明确列出，即使权重占比较小。

## 验证状态

创建时仅验证 skill 格式、文档链接和规则一致性，尚未执行一轮真实的跨仓库进度评估。首次评估后记录实际覆盖、估算稳定性和发现的限制，再基于证据改进方法；不得把格式验证或历史未经完整取证的估计当作流程验收。
