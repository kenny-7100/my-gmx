## 范围与正式规则

当前列出的 Web & App 资产是 `https://gmx.io` 和 `https://app.gmx.io`。检查具体域名、生产入口与功能；仓库中存在代码不证明它已在范围内的生产资产执行。任意子域名、新 Solana 程序和预览环境不能自动视为赏金覆盖目标；不属于赏金范围也不等于内部无需修复。

下表归纳公开 Web & App 的全部 22 个影响条目，等级仅表示条款所列等级，具体发现仍须匹配完整条件和排除项。

| 等级 | 列出的影响 |
| --- | --- |
| Critical（13 条） | 网站/应用不可用；子域接管并涉及已连接钱包；直接盗取用户资金；恶意操作已连接钱包（修改参数、替换合约地址、提交恶意交易）；任意系统命令执行；读取运行中服务的敏感文件/数据；攻击者修改钱包交互流程造成财务损失；修改地址重定向资金；取得服务器 shell；绕过认证；替其他用户签署交易；重定向存款/提款；篡改提交给用户钱包的交易 |
| High（5 条） | 无 JavaScript 的持久静态内容注入/修改；泄露用户机密信息；不涉及已连接钱包的子域接管；**无攻击者参与的界面逻辑错误直接使资金无法追回（排除费用和执行价格）**；提权访问未授权功能 |
| Medium（3 条） | 开放重定向至恶意网站；不涉及已连接钱包、至多一次用户点击即可修改其他用户非敏感信息（含浏览器 local storage）；第三方 API key 泄露并证明可造成资金损失或修改网站 |
| Low（1 条） | **无攻击者参与、导致用户财务损失的界面逻辑错误** |

不能把“存在攻击者”“能盗取资金”“Critical”等设为所有候选的必要条件，否则会漏掉明确在范围内的普通界面逻辑资金损失，以及开放重定向、持久内容注入等条目。High 的资金不可追回条目与 Low 的财务损失条目需要分开匹配，不能仅凭交易金额/参数不一致就宣称永久损失或 High。

Information 明确所有等级均需 PoC；Web & App 需代码，并呈现对范围内资产的最终影响，纯文字解释不算 PoC。依赖包 CVE、静态告警、危险 API 名称或截图只能作为线索。

## 检查时的筛选顺序

以下是结合公开规则与已核实修复案例整理的内部方法；满足后也不保证首次报告、接纳或奖励。

1. **定位真实目标。** 明确版本、入口、受影响功能和生产可达条件。未上线分支可作为内部修复候选，但标明未满足当前赏金资产条件。
2. **匹配具体影响。** 指向上表某项，描述用户/系统实际失去什么。资金问题说明资产、方向、可追回性；非资金问题按对应条目证明影响，不硬凑资金损失。
3. **走通原因链。** 有攻击者时说明其实际能控制的输入、信任边界、需要的权限及用户交互；无攻击者的界面错误说明正常操作、状态变化及错误结果。不把手改源码、DevTools、窃取私钥或假设整个可信后端失陷当成普通外部攻击能力。
4. **主动反证。** 检查输入过滤、编码、认证、链上校验、钱包约束、后续校正、回滚/退款及不可达分支；说明防护是否已经阻断所声称的最终影响。只在本机自改 local storage 的现象，不能冒充修改其他用户状态。
5. **最小验证。** 在允许环境提供可执行、可重复的 PoC 和正常路径对照，验证真实受影响逻辑及结果。Mock 可以隔离副作用，但不能 Mock 出需要证明的漏洞或把正常 revert 算成成功利用。
6. **排除与去重。** 核对最新 Scope、Information、Known Issues、已公开审计/修复和可访问的历史报告。未知是否重复时注明，不能凭未搜索到就宣称首报。相同根因的多个入口合并说明，独立根因单独评估。
7. **给出分层结论。** 有代码线索但缺前提/PoC的，记为待验证；可复现普通缺陷但不匹配赏金条件的，作为内部质量问题；符合公开条件且有实际影响证明的，作为私下报告候选；只有正式接纳证据才称已接纳。

不以告警数、文件数或提交数衡量有效性。不因为目前不能证明而断言无漏洞；缺口应能定位到具体条件、证据或验证步骤。

## 优先过滤的低价值告警与例外

| 线索 | 需要补齐的证据 / 排除边界 |
| --- | --- |
| 依赖漏洞、HTML/脚本注入风险、危险函数调用 | 当前生产构建是否使用受影响路径；输入能否进入；既有防护是否阻断；最终对应哪项影响。无 JS 的持久内容注入本身已列 High，不能统一要求执行 JS |
| URL、地址、交易或签名状态不一致 | 对照用户当前意图和实际发送值，走完消费者链；错误网络/数值不自动等于资金不可追回。也不能要求一定有外部攻击者才验证 |
| 前端包里有 API key 或疑似秘密 | 非敏感环境变量、开源代码、用户名不等于敏感泄露；GitHub 里发现的秘密需证明生产在用。第三方 key 条目还要求证明资金损失或网站修改；验证不得擅自操作第三方系统 |
| 自己在控制台修改状态、自己安装恶意扩展后出错 | 不能替代跨用户影响或正常使用条件。用户机器/浏览器已被攻破、浏览器/插件本身缺陷等被排除 |
| 缺安全 header、最佳实践建议、功能建议 | 单独不构成有效报告；只有证明相应影响且不落排除条款才继续 |
| 服务不可用或依赖宕机 | 可绕过的特定合约 DoS 被排除；界面依赖服务的 DoS 默认 Low，阻止交易或撤出流动性时有例外。托管商自身且 GMX 无法通过配置修复的问题按 Informational。不得实际发起 DoS 或大量流量扫描 |
| 需要管理员密钥、泄露凭据、内部特权、钓鱼/社会工程 | 按完整排除项判断；不能把这些先决条件省略，包装成普通无权限漏洞 |
| 测试/配置文件问题、实验分支行为 | 测试/配置默认排除，除非计划另有说明；仍需核对是否实际进入生产。不能仅因路径含 config 就排除已证明影响生产的代码 |

## 案例校准后的优先检查方向

1. **同一份用户意图贯穿到底。** 对比显示、quote、transfer、签名和执行使用的账户、链、币种/market、金额、价格方向、接收目的地及 TP/SL；不能只比表单值与某个中间变量。GLV、Express、USDG convert-first 和 Limit→Market 的修复共同支持此方向。
2. **每个异步边界核对语义。** 快速编辑、Enter 与 click、quote/RPC 失败、签名排队、切链重试、布局重挂载之后，旧结果是否仍可发送；兼容的 quote 刷新不应机械使签名失效。依据 #3170、#3281、#3284、#3292、#3301。
3. **用链上消费者校验财务计算。** TWAP 分片和费用计提次序、价格相关抵押品、minOutput 的方向与舍入应与真实合约一致；仅有显示偏差不足以说明损失，但显示误导签出的 SL/规模/限价可以有实际影响。
4. **合法第三方输入不等于用户授权。** 权限允许的入账、余额变化不能自动改变用户保存的提款/平仓去向或费用来源。修复中重点看初始化、异步默认值与显式选择的优先级。
5. **安全修复必须覆盖旧状态和直接入口。** UI/SDK 的会话密钥、轮换、撤销、迁移要与已部署合约及其他客户端一致；只修当前按钮或 API 过滤不能证明所有入口被阻断。以公开 review 的最终修复为准，不复制早期方案。

有效候选的最小证据包：目标版本/生产可达依据 → 正常用户意图或可行攻击能力 → 确定的错误 payload/状态 → 对应条款影响及损失条件 → 最小复现与反证 → 重复/已修复检查。**缺哪一段就标明缺哪一段，不用等级标签替代证据。**

## 公开修复可提供的辅助经验

2026-11-28 通过公开 GitHub API 核实 [PR #3034](https://github.com/gmx-io/gmx-interface/pull/3034) 已于 2026-10-06 合并到 `master`，关联 SEC-22。它支持以下通用检查方向：交易声明的目标网络与发送时实际钱包网络必须对应，不能只比较两个来源相同的旧状态；验证需沿实际发送入口和适配器检查。

此处仅保存公开、已合并修复的通用经验，没有读取或复制 SEC-22 的私密正文。**公开修复不证明 Immunefi 已接纳/支付，不证明所有生产环境已部署，也不属于已核实的“11 月 17 条”完整集合。** 更多案例、被替代 PR 和工程/赏金结论区分见[研究记录](gmx-frontend-security-cases-2026-11.md)。

## 获得真实报告后的校准方式

每个可用样本至少核对：报告来源/编号、资产和发生版本、原始触发条件、实际影响、可行前提和用户交互、PoC 证明范围、项目接纳/拒绝/降级的明确理由、最终等级及支付证据（如有）、修复与复验边界。

- 分别标识“正式接纳”“已支付”“项目已修复”“研究员自述”“接纳状态未知”；不互相替代。报告可能因范围、重复或规则被拒绝，即使缺陷真实，也不能归为无意义问题。
- 把相同根因聚类，再归纳“最低有效证据”和“容易误报的反例”；不按单个案例扩大到所有同类函数。
- 有拒绝/降级样本时补充边界；只有正样本时明确无法完整估计误报率，不声称保证命中或保证无漏报。
- 私密样本只在获准渠道读取/保存；版本化文档只存经允许的脱敏通用判断及可安全分享的引用，不记录未修复利用路径、PoC、地址/账户细节或秘密。

当前缺口：11 条关联编号均由工程记录还原，未取得这些 SEC 原始报告的完整正文、最终赏金接纳/支付明细，也未还原产品经理所述 17 条的完整集合。已有 5 条团队确认与上线、2 条 Medium 评定证据可用于校准，但不推断其余状态。另读到一份历史附件报告，其当前路径已被替换，不能算当前有效或已支付样本。

## 私下报告与验证边界

用户提供的产品经理建议明确：可利用信息先私下报告给 **Zeke 或 Orion**，不要直接放入 Linear。用户当前授权是理解公开/获准报告和沉淀筛选方法，尚未要求开始扫描当前业务代码。

后续扫描发现敏感候选时，先在私密、获准位置准备目标版本、影响、必要前提、最小复现及反证结论，交给 Kenny 通过获准渠道报告。不自动建 Linear、公开 issue/PR、提交 Immunefi 或代发消息；不把利用细节写入会自动推送的普通 docs/issue 记录。

按 Information 的禁止活动执行：链上测试使用本地 fork；不测试主网/公共测试网部署代码，不操作第三方预言机/合约/系统，不进行实际 DoS、大量流量自动测试或社会工程。钱包签名、广播和部署仍需各自授权。公开范围里列有某种影响，不等于授权在线实施该攻击。
