# 需求推荐与就绪核验

本流程于 2026-10-24 经用户确认，用于决定下一条最值得实施的 Solana 迁移需求。入口为 [gmx-solana-next-task](../.agents/skills/gmx-solana-next-task/SKILL.md)。核心要求：同时核验 Linear、GitHub PR 和实际代码，使推荐既有推进价值，也具备当前实施与独立交付条件。

## 范围与授权

推荐是分析工作，不代表用户已选择需求或授权实施。需求查询复用[现有工具](linear-requirements.md)，选定需求后的开发遵循[交付流程](linear-development-workflow.md)。本流程不修改线上需求、认领任务、发表评论、创建 PR 或修改业务代码；不自动运行 UI 测试、构建、部署或启动浏览器。

最新上游事实优先从 GitHub CLI/API 读取。本地 remote-tracking refs 不保证新鲜；通过线上分支提交 SHA 与本地引用对照确认。未经授权不执行 fetch/pull、切换分支、更新 `solana-integration` 等 Git 写操作；可以通过 GitHub API 读取指定提交的文件和 diff。工具或权限不可用时标明证据缺口，不把缓存结果当作本次在线核验。

## 需求全貌与候选

1. 每轮推荐先按查询 skill 同步 FESOL 全量需求，阅读正文及状态变化，不只扫描标题。核对项目与标签，旧 `GMTrade` 需求不计入迁移范围；归属冲突按查询规则处理。
2. 筛出少量有竞争力的候选，实时读取候选和关键前置的正文、评论与双向关系，区分关联与阻塞方向。
3. 同时检查父任务、拆分任务、重复/取消项、后续技术范围和设计决策。子任务 Todo 不代表无人实现；父任务 Review 可能已包含子任务范围。完成切片不等于原始端到端需求完成。
4. 沿关键依赖继续追踪到候选实际需要的可用基础，包括正文中未建成 Linear blocks 的依赖。无需每轮深查所有仓库，但不能跳过影响首选结论的关键前置。

## GitHub 与代码证据

候选和关键依赖均须核验相关 PR，不能用 Linear 状态替代。检索先用需求编号及需求中的链接，再结合标题、旧编号、父/子任务、分支和代码路径交叉核对；没有搜到编号不等于没有实现。

| 核验项 | 所需证据与判断 |
| --- | --- |
| PR 身份与状态 | 仓库、URL、open/closed/merged、Draft、base/head、最新 head SHA、合并提交及时间；closed 不等于 merged |
| 实际改动 | 阅读 diff 和相关上下文，确认提供的接口、覆盖范围与候选实际需要一致；不只读标题或 Summary |
| 审查与检查 | 检查最新 head 对应的 CI、自测证据、未解决审查意见和后续提交；旧 head 的通过结果不能当作当前验证 |
| 最新上游基线 | 在线获取 `release` 的 SHA，核对代码仍存在并可供候选使用；检查影响该能力的回退、替代及后续修改，不能只依据曾合并 |
| 开放工作 | 检查候选、原始任务及相邻范围的开放 PR 和负责人，识别重复实现及需要协调的接口；不自动联系他人 |
| 本地与交付差异 | 只读检查当前分支/工作区，区分 `solana-integration`、上游 `release` 和开放 PR 的能力；判断交付是否依赖仅在个人分支的内容 |

对关键实现追踪调用方、状态入口和数据契约。若需要评估正确性或存在影响后续实施的审查问题，按[编码与自审规范](coding-and-self-review.md)阅读相应 gmx-prompts 入口；推荐不等于对全部相关 PR 完成完整代码审查。

## 实际前置与验收

需求状态、代码状态和运行可用性分开记录。跨仓库或服务依赖按候选范围核验：

- API 字段、金额精度、地址语义、错误/不可用状态和数据新鲜度；样例是否已评审，服务返回样例还是真实数据。
- SDK 包版本、源码 tag、IDL 与部署程序的适用版本；相关计算和指令契约是否确认。
- 必要的部署、服务权限、配置、测试钱包、资金、lookup tables 和功能开关。只在授权范围内做必要的只读核验，不发送交易或改变配置，不输出密钥。
- 哪些验收能通过单元/契约检查证明，哪些必须由用户手动 UI 或主网验证，以及这些条件现在是否具备。

依赖满足与否按本次切片判断：纯函数、原始读取或已评审样例切片不必等待完整交易链路；真实交易和数据验收不能由模拟数据、未评审字段或源码存在替代。缺少用户必须提供的资源时，暂停相关核验，说明用途和配置位置，不自行绕过。

## 比较与输出

比较主线推进价值、实施就绪程度、独立交付范围、验收可行性、重复与返工风险，以及能提前消除的精度/安全/状态风险。不能只按任务简单程度、Linear 优先级或阻塞数量选取，也不编造工期和量化分数。优先级每轮重算，不保存固定的需求编号排序。

推荐应简洁并提供可复核证据：

1. 一个首选及为何现在实施。
2. 关键前置表：需求、Linear 状态、PR/上游代码证据、当前是否满足，以及协调或交付限制。
3. 与主要备选的比较，说明未优先选择的实际原因。
4. 最小交付范围、可证明的验收结果和待用户手动验证项。
5. 核验时间、上游基线 SHA、关键 Linear/PR/代码链接，未确认事项及会改变推荐的条件。

明确区分“需求层面无阻塞”“代码基础具备”“可独立交付”和“运行条件可用”。关键证据缺失时只给暂定推荐；若缺口足以改变选择，说明尚不能确认首选，并指出所需证据。不能为了给出确定答案而猜测。
