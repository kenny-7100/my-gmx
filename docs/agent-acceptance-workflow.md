# Agent 需求验收映射

更新日期：2026-10-25。对应 A07；首阶段交付为工作表、执行流程与 [FESOL-55 实例](acceptance/FESOL-55.md)。已补充 `yarn agent:acceptance` 对现有 Markdown 工作表做离线一致性检查，见下文。这是个人测试验收基础设施，不修改业务实现或 Linear 状态，也不替代[需求交付流程](linear-development-workflow.md)。

## 先映射，再执行

后续 Agent 开始需求验收时按以下顺序执行，而不是先跑全部预检：

1. 按[需求工具说明](linear-requirements.md)实时查询目标需求的正文、评论、关系、项目和标签，记录抓取时间与 updatedAt。核对当前任务的授权和交付版本；Linear 的 Done 不是验收证据。涉及实现方案不明或冲突时先澄清，不自行改写验收标准。
2. 复制[工作表模板](acceptance/template.md)，将正文 Scope、Acceptance 及有效补充要求逐项编号。一个条件可分多个验证层次，但不得遗漏原要求；非本轮范围保留为 not-run 并说明原因，不从表中删除。
3. 为每行确定环境、数据模式、预期结果、执行方法和证据。涉及 PR 页面时，按[本地预览定位](agent-preview.md)先绑定实时 PR head 与不可变部署 URL，再执行已获授权的页面验证；部署元数据不当作页面功能证据。先区分单元/mock、样例 HTTP、本地产物、真实只读、浏览器与真实交易，避免选错证明方式。遇到必须由用户提供资源的项标 blocked，暂停依赖工作，其他独立项继续。
4. 只准备当前条件需要且已获授权的依赖，按[执行前顺序](coding-and-self-review.md#执行前的环境检查与顺序)选用现有工具。单元 loader 验收无需启动 RPC/API 或读取钱包；价格、资金、ALT、部署相关条件才运行对应检查。不要机械重复统一预检与同一单项命令。
5. 记录开始/结束时间、完整命令、退出码及原始日志。每行给出结果和证据；失败与未执行不得写成通过。涉及异步任务时等待退出码，不能只根据日志里的 passed 字样判断。
6. 先按下表汇总，填写工作表并执行下文一致性检查，再列出未覆盖条件、原因及继续操作；更新基础设施清单中的相关状态。工具本轮完成与业务需求验收结论分开填写，不能用工具通过替代业务需求通过，更不能因此自动关闭需求或父任务。

## 状态约定

| 状态 | 使用条件 | 不能表达的含义 |
| --- | --- | --- |
| passed | 当前行所写范围已执行，预期满足，证据、版本及退出结果可核实 | mock passed 不代表真实页面或链上流程 passed |
| failed | 已执行但结果不符合预期，或检查命令错误退出 | 不得把错误当空数据、零余额或成功 |
| blocked | 该行需要的已确认资源、权限或用户决策缺失，无法继续 | 普通未执行或仅未获本轮 UI/构建授权用 not-run |
| not-run | 本轮未执行该项，写清原因与下一步 | 静态看到代码或历史报告不代表本轮已执行 |
| partial | 一个复合条件仅部分验证，或整体仍有未覆盖项；列出子项状态 | 不能隐藏 failed/blocked，不能当成全部通过 |

汇总规则：出现 failed 则整体 failed；无 failed 但有 blocked 则整体 blocked，同时列出已覆盖部分；无前两者且全部 required 条件 passed 才为 passed；全未执行为 not-run；其余为 partial。人工步骤一旦执行并满足条件，也可 passed，需附证据。模板中的占位符必须替换后才能作为有效报告，不能把空表默认算通过。

环境预检的状态是该工具的结论，映射时要回到需求的预期。例如真实 `solanaTrading` 缺失对“交易前置就绪”是 blocked，对“缺失时检查返回 false”是可验证输入；仍需执行检查函数才能证明后者，不能直接把 keeper 报告移为 passed。

## 证据与共享

- 每份报告写明仓库、commit、dirty 和测试时相关文件的身份。dirty=true 时提供相关文件摘要或补丁范围；源码版本、本地产物和线上部署分开记录。仅凭 HEAD 不能还原未提交修改。
- 默认原始产物放在 `.local/acceptance/requirements/<issue>/`，沿用现有工具输出，不建平行业务 runner。文件被 Git 忽略，其他机器不保证存在；在共享 Markdown 中保留命令、时间、版本、结果、关键公开摘要和证明边界，明确原始文件可用性。需要移交原始证据时按项目批准渠道归档，不能声称本地路径是共享附件。
- 已有 Solana 签名时，按[交易回执证据](solana-transaction-evidence.md)记录 finalized 结果和完整回执摘要，仍将 keeper 执行/最终持仓列为独立条件；不靠交易成功直接推断订单成交。
- 移交已有工具 JSON 报告时，按[证据包说明](agent-evidence.md)显式选取文件并打包，在可信交接记录保存 manifestSha256；工作表本身也归档时按证据包文档显式绑定，冻结后不写回包摘要，接收后用 `verify --expected-manifest-sha256` 离线验证并确认 matched。保留原始观察时间和状态，不把包完整性通过当业务验收通过。
- 不记录助记词、私钥、配置文件内容、完整带凭据 URL 或钱包会话。公开地址和公开文件摘要可记录。不得整份拷贝环境变量到报告。
- 需求 updatedAt、相关代码/配置/产物、依赖版本或目标环境变化时，重新判断哪些证据失效；历史 passed 保留日期，不自动沿用为本次结果。先比较范围再重跑必要项，不要求无关检查全量重跑。

## 工作表自动一致性检查

适用时机：工作表填写完成、准备交接或报告结论前。工作目录为主仓库根目录：

```sh
yarn agent:acceptance --file docs/acceptance/FESOL-55.md
```

实现：[scripts/agent-acceptance.mjs](../scripts/agent-acceptance.mjs)；测试：`yarn test:agent-acceptance`。仅用现有 Node，无网络、秘密配置、服务启动、浏览器或交易；只读取指定 Markdown 和检查器自身，不改写工作表、不执行表内命令、不访问引用路径或更新历史观察时间。

使用[现有模板](acceptance/template.md)的两张表作为唯一输入，不另外填写 JSON：

- 保留条件表与执行记录表的列名及顺序；每张表只能出现一次，单元格非空，保留各表所属的二级章节标题，条件表中间不能插入空行或说明文字。条件 ID 为唯一 R1、R2 等，证据 ID 为唯一 E0、E1 等；不要求编号连续，不能借此判断需求是否遗漏。
- 单独一行填写 `- 业务需求验收结论：partial；...`，状态只能是 passed、failed、blocked、not-run、partial。条件的状态单元格只填状态，unit/mock 等范围写在环境与证据列。
- 所有条件参与汇总。failed 优先于 blocked；全部 passed 才 passed；全部 not-run 为 not-run；其余 partial。未执行层次保留，不能删除原要求来取得 passed。
- passed、failed、partial 行的证据列必须引用执行记录中的 E 编号。passed 不得引用错误退出或人工失败的执行记录。blocked、not-run 可无执行证据；无记录时保留执行表的表头和分隔行，删除占位记录。所有非 passed 行必须写下一步，不能只填破折号。
- 执行记录的退出码/结果只能填非负整数（最多三位）或 `manual-passed`、`manual-failed`；时间、命令、原始产物及摘要作为必填文本，不自动解释。对异步任务记录最终退出码，不把启动成功写成最终通过。
- 这是受限 Markdown 格式，不支持 fenced code blocks、HTML 注释/标签、尖括号占位符及表格单元格内的 `|`（包括反引号或转义形式）。表内命令若含管道，应引用外部脚本并在该脚本中表达；不静默解析不支持的表格结构。未填模板应失败。

| 退出码 | 含义 |
| --- | --- |
| 0 | 工作表一致，且所有条件 passed |
| 1 | 工作表不合法/不一致/读取失败，或合法工作表的需求结论为 failed；由 JSON 字段区分 |
| 2 | 工作表一致，但需求结论为 blocked、partial 或 not-run |

JSON 中 `scope: acceptance-worksheet-consistency` 与 `status` 仅表示内部检查结果；`requirementAcceptance` 为按所列条件计算的结论。合法的 failed 工作表仍可有 `status: passed`，但退出 1；消费者应同时查看 scope、requirementAcceptance 和退出码。`requirementCoverage`、`evidenceSufficiency` 固定为 not-evaluated：工具不验证需求映射完整性、原始产物存在/摘要真实性、数据新鲜度、版本有效性或业务正确性，也不替代实时 Linear 核对。报告包含本次检查时间、工作表与检查器 SHA-256，不能把检查时间当历史证据执行时间。此报告可按[工作表移交说明](agent-evidence.md#工作表与检查报告一起移交)，与对应 Markdown 显式绑定后进入证据包。

FESOL-55 实例是历史工作表，适配本格式后仍为 partial，不视为本轮重新执行业务验收。新增条件、修改状态或证据后重新运行此命令；历史不受影响的原始执行不机械重跑。
